# Одноразовая настройка Timeweb для изолированного сайта

Это **не Laravel**, но используется та же структура: в HTTP доступен только `public`; PHP код и `storage` лежат вне него. Изоляцию сайта Timeweb можно оставить включённой, если он имеет доступ к своей директории. Запись фактически проверяет скрипт перед переключением.

## Итоговая файловая структура

```text
~/
├── public_html -> /home/ACCOUNT/put-bez-pregrad/public   (символическая ссылка)
├── public_html.pbp-backup-YYYYMMDDHHMMSS/                 (откат)
└── put-bez-pregrad/
    ├── public/               (HTML/JS/CSS, открытые PHP-точки входа)
    ├── app/
    │   ├── api/              (заявки, SMTP, антиспам, PHPMailer)
    │   └── admin-api/        (логин, пароль, настройки)
    ├── storage/              (НЕ передавать через FTP, права 700)
    │   ├── state.php         (пароль, контакты, SMTP)
    │   ├── form-challenge.key
    │   └── rate_*.php
    └── tools/activate.sh     (одноразовое переключение с откатом)
```

Корневой каталог **настоящего основного сайта**: `~/public_html`. Если у сайта другой корень, не выполнять активацию без адаптации путей. `public_html` после переноса будет ссылкой, браузерный URL не меняется.

## От владельца нужно один раз

1. В панели Timeweb включить **SSH**: Дашборд → Статус сервисов → SSH. Пароль панели и SSH-ключи в чат не присылать.
2. Зайти под **основным пользователем** по SSH (Windows PowerShell: `ssh ЛОГИН@СЕРВЕР.timeweb.ru`, порт 22). Имена сервера и логин доступны в панели Timeweb.
3. На сервере выполнить **только**:

   ```bash
   mkdir -p ~/put-bez-pregrad/storage
   chmod 700 ~/put-bez-pregrad/storage
   printf 'pbp-isolated-site-root-v1\n' > ~/put-bez-pregrad/.pbp-ftp-root
   ```

4. В Timeweb создать отдельного FTP-пользователя с доступом **только к `~/put-bez-pregrad`**. В GitHub Secrets обновить `TIMEWEB_FTP_HOST`, `TIMEWEB_FTP_USER`, `TIMEWEB_FTP_PASSWORD`; `TIMEWEB_FTP_DIR` = `/`, если пользователь ограничен этим каталогом, либо абсолютный путь к каталогу `put-bez-pregrad` **от корня разрешённого FTP-доступа**. Нельзя оставлять FTP с корнем старого `public_html`: серверный PHP-код окажется под HTTP.
5. В GitHub Actions вручную запустить **Deploy isolated site to Timeweb** → `phase: stage`. Этот шаг просто загружает проект в отдельную папку, не меняя продакшен.
6. После успешного `stage` в том же SSH выполнить:

   ```bash
   bash ~/put-bez-pregrad/tools/activate.sh
   ```

   Скрипт перенесёт прежние `state.php` и ключ формы из `~/.pbp-private/` (при наличии), **проверит из действующего PHP**, что `storage` доступен на запись, и только затем переключит `public_html`. Если PHP не может писать или новое API не работает, прежний сайт останется/будет восстановлен.
7. В GitHub Actions запустить **Deploy isolated site to Timeweb** → `phase: release`: workflow проверит, что первый этап уже активирован, установит пароль администратора через защищённый одноразовый обработчик, удалит его и проверит публичный API и закрытые URL.
8. После релиза войти в админку, сохранить SMTP-реквизиты (если `state.php` отсутствовал) и проверить доставку тестового письма. До реального письма нельзя считать форму полностью исправленной.

**Никогда не запускайте старый FTP-деплой в `public_html` после изменения структуры.** Рабочая папка для FTP — `put-bez-pregrad`, а для HTTP — её `public`.

## Особые случаи

- Если сайт в Timeweb не основной, команда `activate.sh` для него не подходит — она специально защищена от произвольных путей. Нужно уточнить каталог сайта.
- Если PHP-тест записи даёт ошибку, скрипт не переключит сайт. Не отключайте изоляцию и не ставьте права 777.
- Если есть состояние в `.pbp-private/state.php`, но копирование завершилось ошибкой, скрипт остановится, чтобы не потерять SMTP/пароль. Сам `.pbp-private` не удаляется.
- После успешной активации старый `public_html` лежит в `~/public_html.pbp-backup-...`. Резервную копию не удаляйте, пока не проверены авторизация и SMTP.
- Доступ через обычный FTP не шифрует пароль. Не используйте основной пароль аккаунта Timeweb, лучше отдельный ограниченный FTP-пользователь.
- Новые публикации после активации используют `phase: release` и не стирают `storage`.
